# L2 事实记忆：冲突消解与派生链

> 本文是 L2 的规划书 + 实现台账。对应架构总览见 [四层记忆架构与进展.md](四层记忆架构与进展.md)。
> 状态：🚧 实现中（2026-09-18 起）——进度见文末台账。

## 1. 为什么要动 L2

L2（`memories` 表 + MCP 读写工具）是四层里唯一「先于重构就有」的层，也是文档承诺与实现差距最大的层。两个缺口：

**缺口 A：L2 不在 L0 的派生链上。** 架构文档写「L0 是唯一事实源，上层均可从 L0 重放重建」，
但代码里只有 L1 读 `l0_records`。L2 的输入全部来自 MCP `add_memory` 的外部推送
（`createMemory` → `events` 队列 → `processMemoryMaterial` → `extractMemories`），
没有任何从归档派生的路径。后果：换 L2 的提炼算法无法"清指纹重跑"——**没有源可重放**。

**缺口 B：缺 mem0 最核心的机制。** 调研文档写明「L2 用 mem0 的 ADD/UPDATE/DELETE/NOOP
四操作控制记忆膨胀——这是'自动凝练'不失控的核心机制」。但当前 `processMemoryMaterial`
是 `extractMemories` → `insertMemory` 纯追加：**不与已有记忆做任何比对**。
结果是同一事实反复入库（"服务部署在 10.10.10.88" 每提一次就多一条），
信息更新时新旧并存且互相矛盾，检索结果被冗余淹没。
`updateMemory`/`deleteMemory` 只作为 MCP 工具存在，需人工调用。

一句话：**L2 手写了 mem0 的抽取那一半，缺了消解那一半。**

## 2. 目标 / 非目标

**目标**

1. 写入路径具备冲突消解：新事实入库前与已有记忆比对，产出 ADD/UPDATE/DELETE/NOOP。
2. L2 接入派生链：从 L1 摘要（而非原始归档）派生事实，静默触发、指纹幂等、可重跑。
3. 向量检索层可插拔：embedding 缺失时全链路可用（关键词兜底）；具备时走真正的向量索引。
4. 保留既有 MCP / REST 接口语义不变；为新前端补齐后端聚合接口。

**非目标**

- 不引入 mem0 / Letta 等外部运行时（结论见记忆与调研：JS 包是客户端、引擎需 Python + Qdrant，
  与单用户自托管 + SQLite 的部署形态冲突）。
- 不做 L3 画像层。
- 不追求前端展示（前端由另一路并行重构）。

## 3. 设计

### 3.1 四操作语义

| 操作 | 触发条件 | 落库动作 | 审计记录 |
|---|---|---|---|
| **ADD** | 全新事实 | 插入新记忆 | `op=ADD`，`after=新文本` |
| **UPDATE** | 同一事实、新版本是在旧信息上补充/修正 | 覆盖文本（保留 id），重算向量 | `op=UPDATE`，`before`/`after` 都记 |
| **DELETE** | 旧记忆被新事实**完全取代**（换了取值） | 删旧记忆 **+ 存入新事实** | `op=DELETE`（记 `before`）+ `op=ADD`（记 `after`） |
| **NOOP** | 已存在等价记忆（新事实无增量） | 不动 | `op=NOOP`，`target=已有 id` |

**DELETE 为什么必须「删旧 + 存新」**：初版实现把 DELETE 当成纯删除，**真实模型复验时立刻暴露问题**——
给它「端口从 18543 改成 18544」，deepseek-chat 选了 `DELETE M1` 而不是 `UPDATE`，
结果旧记录被删、新取值凭空消失，冲突消解反而变成了数据丢失。
修正后 DELETE 语义是「取代」：删旧并入新，模型不管选 DELETE 还是 UPDATE 都不会丢事实。

**为什么 DELETE 是硬删 + 审计表，而不是软删（`superseded_by`）**：
`memories` 表加列需要迁移，且"旧事实不删只标记"是 L3 的诉求（双时间轴），不是 L2 的。
L2 的性质是**可从 L1/L0 重派生的视图**——删错了重新派生即可。
审计表 `memory_ops` 保留原文，兼顾可追溯与可复原，同时不动 `memories` 的现有 schema。

### 3.2 数据流

```
写入路径（保持既有异步语义不变）
  MCP add_memory(text/messages)
    → events 队列 → processMemoryMaterial
    → extractMemories(LLM 抽取)                    ← 既有
    → reconcileFacts(新)                            ← 本次新增
         候选召回（关键词，无 embedding 也可用）
         → 判定（1 次 LLM 调用，批量）→ 四操作
         → 应用（memories 增/改/删 + memory_ops 审计 + 向量同步）

派生路径（补齐缺口 A）
  L1 摘要（l1_summaries, status=done）
    → l2_sources 指纹幂等（静默 + 未变则跳过）
    → 1 次 LLM 调用：从摘要中筛出「值得长期记住的事实」并直接消解
    → 同一套应用层（memory_ops.source = 'l1:<agent>/<session>'）
```

### 3.4 无 embedding 下的候选召回

冲突消解的质量取决于"能不能找回相关的已有记忆"。本机没有 embedding 服务，
且生产环境 embedding 是可选组件，因此**候选召回必须不依赖向量**：

1. 分词：抽 CJK 连续串与拉丁词/数字（长度 ≥3）。
2. FTS5 trigram 召回：`memories_fts MATCH '"词1" OR "词2"'`，按 bm25 取 topN。
   （trigram 无法索引 <3 字符片段，中文双字词会漏——这正是下面第 3 步存在的理由）
3. 兜底：无 ≥3 字符词根时，取该用户近期 N 条 + JS `includes` 过滤。
4. 有向量时叠加语义召回（`vec.js`），两路合并去重。

召回是"宁可多带、不可漏"（判定由 LLM 做），因此用 OR 而非既有检索的 AND。

### 3.5 Token 预算（硬约束）

用户明确要求省 token，故：

| 措施 | 参数（env 可调） | 效果 |
|---|---|---|
| 判定批量合并 | 一次素材/会话 = **1 次** LLM 调用 | 而非每条事实一次 |
| 输入裁剪 | `L2_MAX_FACTS=20`、`L2_MAX_CANDIDATES=6`、单条 ≤200 字符 | 单次输入 ≈1.5–3K token |
| 输出上限 | `max_tokens=800` | 只输出 ops JSON |
| 模型 | `deepseek-chat`（非 reasoner），temperature 0 | 最便宜档 |
| LLM 不可用 | 直接走"全部 ADD" | **0 token**，且不阻塞写入 |
| 测试 | 全部 stub `llm.complete` | 0 token |
| 真实端到端 | 仅 2–3 次极小调用 | 目标 < 5K token 总量 |

预估：单会话派生 ≈ 1.5K 输入 + 0.3K 输出 ≈ ¥0.002（deepseek-chat）。

### 3.6 安全阀（防模型乱来）

模型输出不可全信，尤其 DELETE。硬约束：

- `op` 必须是四个合法值之一，否则该条降级为 ADD；
- `UPDATE`/`DELETE` 的 `target` 必须**落在该条事实的候选集内**且属于当前用户
  （防幻觉 id、防跨用户误删）；
- `UPDATE` 缺 `text` 或文本为空 → 降级为 ADD；
- 单批次 DELETE 数量上限 `L2_MAX_DELETES=5`，超出的记 skipped 不执行；
- 判定失败 / JSON 解析失败 → **全部 ADD**（不让增强功能导致数据丢失）。

## 5. 风险与回滚

| 风险 | 应对 |
|---|---|
| 模型误判导致误删 | 候选集内校验 + DELETE 上限 + 全量审计表可复原 |
| 判定变慢拖累写入 | 判定在后台 `events` 队列里跑（既有异步语义），不阻塞 MCP 返回 |
| 并发会话改同一文件 | 只做精确匹配的追加式编辑；新逻辑全部放新文件 `src/l2/` |
| sqlite-vec 装不上/维度不匹配 | optionalDependency + try/catch + 维度校验，失败即降级关键词 |
| 成本失控 | 批量 1 次调用 + 硬上限 + stub 测试，真实调用仅个位数次数 |

**回滚**：`reconcileFacts` 与派生调度均可通过 env 关闭（`L2_RECONCILE=0` / `L2_DERIVE=0`），
关闭后行为等价于改动前（纯追加）。新表只增不改，无需回滚迁移。

## 8. 怎么开、怎么关、怎么回滚

**开**：默认全开。`.env` 里 `L2_RECONCILE=1`、`L2_DERIVE=1`、`L2_VEC=1`（见 `.env.example` 的 L2 段）。
服务启动即自动跑派生调度（与 L1 并列），无需额外操作；也可 `POST /api/l2/run` 手动触发一轮。

**关**（任一层出问题时的隔离开关，都不需要改代码）：

| 开关 | 效果 |
|---|---|
| `L2_RECONCILE=0` | 写入退回纯追加（等价改动前行为，0 token） |
| `L2_DERIVE=0` | 不启动派生调度（L1→L2 链路停用，其余不受影响） |
| `L2_VEC=0` | 向量索引停用，检索退回"全扫 + JS 余弦" |

**回滚**：新表（`memory_ops`、`l2_sources`、`l2_meta`、`memories_vec`）只增不改，`memories` 表结构未动，
故回滚只需还原代码 + 设上述开关，**不需要数据迁移**。要彻底重来：清空 `l2_sources` 即会让所有会话重新派生；
`memory_ops` 记录的被删原文可用于人工复原误删的记忆。

## 更新路径的局部重消解（2026-09-19）

`update_memory` 改文本后异步触发一次**重复检测**（`reconcileAfterUpdate`，fire-and-forget，不阻塞响应）：
更新后的文本与候选记忆比对，若被判定为「同一事实」（仅措辞不同、取值一致），删除**旧候选**、保留刚更新的条目。

- 安全阀：目标必须在候选集内（防幻觉 id）；单次至多合并 1 条；取值不同的"新旧版本"不在此处理
  （那是写入路径四操作的职责）；LLM 失败/输出不可解析 → 静默跳过；刚更新的条目永不被本流程改动。
- 审计：删除记 `memory_ops`（`source=update_reconcile`，`before_text` 可复原）。
- 开关：沿用 `L2_RECONCILE`；无邻居可比时 0 次 LLM 调用。
