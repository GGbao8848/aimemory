# L0 原始会话归档（采集器方案）

> 目标：把各台机器上 agent（Codex / Claude Code / ZCode）的**原始会话**自动备份到 aimemory 服务端，
> 只追加、不改写、不做 AI 加工。这是四层记忆里的 **L0 层**——唯一事实源。

## 1. 分层定位

参考《会话与记忆管理系统调研报告》的四层模型：

| 层 | 内容 | 本项目状态 |
|---|---|---|
| **L0 原始会话** | agent 会话原文（append-only） | ✅ 本方案（本文档） |
| L1 会话摘要 | 每会话的 LLM 摘要（情景记忆） | 待建（从 L0 重放生成） |
| L2 事实记忆 | mem0 式抽取的事实条目 | ✅ 已有（`memories` 表） |
| L3 画像／知识 | 长期凝练、双时间轴 | 未建 |

关键原则：**原始层与凝练层分离**。L0 只负责忠实记录，凝练逻辑再怎么升级，都能从 L0 重放重建，
不会丢数据。也正因如此，L0 的写入路径刻意不接 LLM / embedding。

## 2. 架构

```
┌── 各台设备 ───────────────────────────────┐        ┌── aimemory 服务端 ──────────┐
│  采集器（pm2 常驻 · 死程序）                │        │                              │
│                                            │        │  POST /api/l0/ingest         │
│  ┌──────────┐   ┌──────────────┐          │  HTTP  │    ├ 鉴权（多 Token）         │
│  │ adapter  │→ │ 归一化记录流  │→ 上传器 ──┼───────→│    ├ 批次幂等（_bid）        │
│  │ codex    │   │ (固定 schema)│          │        │    └ append→ data/l0/…jsonl  │
│  │ claude   │   └──────────────┘          │        │                              │
│  │ zcode    │     ↑ 游标 + 队列            │        │  GET /api/l0/stats（对账）   │
│  └──────────┘     （~/.aimemory-collector）│        │                              │
└────────────────────────────────────────────┘        └──────────────────────────────┘
```

**"死程序"的含义**：上传器只认归一化 schema，它不知道对面是哪种 agent。新增 agent 只加 adapter，
上传器一行都不改；agent 升级改格式也只改对应 adapter。接口一旦冻结，上传层就长期不动。

## 3. 归一化 schema（adapter 与上传器的唯一契约）

一行一条记录：

| 字段 | 说明 |
|---|---|
| `rid` | 稳定标识 `agent:session:native_id` —— L1 据此 upsert 去重 |
| `ts` | 事件时间（ISO8601） |
| `version` | 版本号，同一 rid 原地更新时递增（ZCode 用 `time_updated`；L1 取最大版本） |
| `seq` | 会话内顺序号（可选） |
| `role` | `user` / `assistant` / `system` / `tool` / `reasoning` / `meta` |
| `content` | 正文（工具事件为入参或输出） |
| `meta` | agent 特有信息（工具名、模型、cwd…） |
| `raw` | 该条原始数据（L0 是事实源，默认保留；`AIMEMORY_KEEP_RAW=0` 可关，省约一半体积） |

落盘时会再加 `_dev`（设备码）、`_agent`、`_bid`（批次指纹）与 `_recv`（服务端接收时间）——
每一行都自述来源，即使归档文件被单独取走也能审计。

## 3.1 设备维度（跨机归类）

**只按 agent 归类是不够的**：一个人可能有多台机器、每台机器有多个 agent。因此每次上传都携带
**设备三元组**——设备码 + 设备信息 + agent：

```
POST /api/l0/ingest
{
  "agent": "codex",
  "session_id": "sess-xxx",
  "device": {
    "code": "dev_32def8ee",            // 稳定设备码：首次运行生成后落盘，之后不变
    "label": "我的笔记本",              // 人类可读名（默认主机名，可配置）
    "info": { "hostname": "...", "platform": "darwin", "arch": "arm64",
              "os_release": "...", "node": "...", "cpus": 8, "mem_gb": 16,
              "user": "...", "collector_version": "1.0.0" }
  },
  "records": [ ... ]
}
```

归档路径因此变成 `<user>/<设备>/<agent>/<会话>.jsonl`，于是可以：

- 在**任意一台机器**上打开 Web「会话归档」，看到所有设备及其会话，回答"另一台机器做了什么"；
- 按设备过滤（`GET /api/l0/stats?device=dev_xxx`）或按设备+agent 定位；
- 点进会话看逐条详情（用户/助手/工具/推理分类，可展开原始字段）。

设备码的稳定性：存在状态目录 `~/.aimemory-collector/device.json`，重启、改主机名、换 IP 都不变。
**换 Token 重装采集器仍是同一设备**（只要状态目录还在），历史归档不会被割裂成两台设备。

### 统一设备：机器指纹（跨重装仍认回同一台）

设备码本身是随机的，删掉状态目录重装就会变。为此采集器额外上报**机器指纹**——
从机器固有属性推导的加盐哈希（`fp_xxxxxxxxxxxxxxxx`），服务端凭它把新设备码**认回原设备**：

```
采集器                          服务端
  device.code = dev_new（重装后新生成）
  device.fingerprint = fp_8f5e...
        ├──────────────────────► 按指纹查到已登记设备 dev_old
        │                        → 数据归到 dev_old，不新建设备
        ◄──────────────────────┤ 返回 device_code = dev_old
  本地设备码自动对齐为 dev_old（落盘）
```

因此**重装、清状态目录、换 Token、换设备名，仍是同一台设备**，归档路径与历史数据不受影响。

指纹取值优先级（越靠前越稳）：

| 顺序 | 来源 | 说明 |
|---|---|---|
| 1 | `machine-id` | Linux `/etc/machine-id`、macOS `IOPlatformUUID`、Windows `MachineGuid`。与网卡无关，插拔网线/切 WiFi 都不变 |
| 2 | `mac` | 物理网卡 MAC，**排序后取第一个**，排除虚拟接口（docker/veth/br-/virbr/tun/tap…）与全零/组播/本地管理地址 |
| 3 | `hostname` | 最弱，仅当上面都拿不到 |
| 4 | `random` | 兜底，退化为"每次重装都是新设备" |

> **为什么 MAC 只作兜底而不单用**（用户提议用 MAC，实现时按此处理）：多网卡时接口枚举顺序不稳定、
> 笔记本 WiFi/有线切换会换 MAC、容器与虚拟机的 MAC 常被重置、MAC 也可以被改。
> `machine-id` 更稳，故首选；MAC 作为跨平台兜底。即便用 MAC，也必须**排序取第一个并补扫 down 接口**
> ——`os.networkInterfaces()` 不列出已 down 的接口，只从它取会在"换根网线"时改变指纹。

**隐私**：原始 MAC / machine-id **绝不外传**——出机器前先加盐哈希，服务端只见到 `fp_` 哈希，
不持有硬件标识本身。Web 设备卡片显示指纹与其来源（如"系统安装标识"）便于辨认；
没有指纹的历史设备显示「⚠ 无指纹」，采集器下次上报时自动回填。

> ⚠️ **克隆虚拟机镜像**可能 machine-id 与主机名都相同 → 会被认成同一台设备。
> 此时用 `AIMEMORY_DEVICE_CODE` 显式指定设备码区分。

> **设备名保护**：采集器上报的 label 若等于主机名（默认值），不会覆盖服务端已有的自定义名；
> 只有显式设置 `AIMEMORY_DEVICE_LABEL` 才改名。

**设备码不绑定密钥**是刻意的：设备身份属于"机器"，Token 属于"授权"，二者生命周期不同。

## 4. 三家数据源与增量策略

| Agent | 位置 | 增量方式 |
|---|---|---|
| **Codex** | `~/.codex/sessions/YYYY/MM/DD/rollout-<ts>-<uuid>.jsonl`（+ `archived_sessions/`） | 文件 offset（纯追加，最友好） |
| **Claude Code** | `~/.claude/projects/<项目>/<会话>.jsonl`（+ `.orphaned-*` / `.superseded-*` / `subagents/`） | 文件 offset + 改名感知 |
| **ZCode** | `~/.zcode/cli/db/db.sqlite`（表 `session`/`message`/`part`） | **水位线 + 重叠窗口 + 版本号** |

三家各自的坑（实现里已处理）：

- **ZCode 不是追加写**：实测 18622 条 message 中 16140 条 `time_updated > time_created`，
  消息在生成过程中被反复更新。故用「水位线 + 5 分钟重叠窗口」重读窗口内行，产出带
  `version` 的记录；重复由 L1 按 `rid+version` 收敛。DB 以**只读**方式打开，不抢 WAL 锁。
  另外要展平：`message` 是外壳、`part` 才是内容，且 `step-start`/`step-finish`/`timeline`
  是纯 UI 噪音（实测占比约一半），直接跳过。
- **Claude Code 默认 30 天清理**（`cleanupPeriodDays`）：采集器必须尽早装、长期跑，
  晚装一天就永久缺那一天的历史。
- **Claude 会话结束会改名**（`.jsonl` → `.orphaned-*`）：按会话 id 归组识别，避免改名后
  被当成新文件从头重读。

## 5. 可靠性（"不丢不重"）

| 保证 | 实现 |
|---|---|
| 幂等（批次） | 批次指纹（内容寻址）→ 服务端重复批次直接跳过 |
| 幂等（记录） | `l0_records` 表按 `(设备, agent, 会话, rid, version)` 去重。**批次指纹挡不住"同内容不同分块"**——批大小调整或顺序变化会改变指纹，服务端会重复落盘，故必须有记录级兜底；同一 rid 的不同 version 仍保留（ZCode 原地更新靠版本收敛） |
| 断点续传 | 游标与队列元数据原子落盘（唯一临时文件 + rename），批内容单独写 spool，`kill -9` 后从断点继续 |
| 离线容忍 | 上传失败/断网 → 积压本地队列，指数退避，恢复后按序补传 |
| 活跃会话 | 半行保护：尾部未写完的 JSON 行不解析，offset 停在最后完整换行处 |
| 不堵死 | 413（批次过大）就地二分重试；毒批移队尾不阻塞后续；超限触发背压（只传不采） |
| 不静默失败 | 采集异常计数上报，`--status` 可对账本机与服务端；`--dry-run` 部署前预览采集量（零副作用） |
| 单实例 | `state.lock` 进程锁互斥；崩溃残留的陈锁自动接管（按 pid 存活探测） |
| 稳态省 IO | 脏标记：无新数据时不写盘（15 秒一轮、一天近六千轮，稳态几乎零写） |
| 内存可控 | adapter 分页读取 + 边采边 emit（不把整轮结果攒在内存里）；稳态常驻约 110MB |

> **冷启动回填的内存现实**：首次回填要一次性把存量会话（单机实测 3.5 万条 / 147MB）过一遍，
> 峰值约 400MB，且 V8 扩张后不立即归还 OS。`max_memory_restart` 设太小（如 300M）会导致
> 回填期被反复杀掉重启——症状是**错误日志为空、只有 restarts 计数增长**（SIGKILL 特征）。
> 当前设 700M。稳态远低于此。

> **队列用 spool 目录而非内联状态**：若把批内容内联在 `state.json`（每轮整体重写）会涨到
> 上百 MB（实测 144MB）。改为内容写 `spool/<batch_id>.json`、状态文件只留元数据后，稳态约 1MB。
> 崩溃在"写完内容、未提交元数据"之间只会留下孤儿 spool 文件，启动时自动清理（`sweepSpool`）。

> **对账口径**：`GET /api/l0/stats` 的 `records` 取自 `l0_records`（真实落盘的唯一记录数），
> **不是** `l0_batches.records` 的累计值——后者是"累计接收量"，历史重复批次会让它虚高，
> 不能当作归档规模。两者不一致时以 `l0_records` 为准。

## 6. 服务端存储

- 归档目录：`data/l0/<user_id>/<device_code>/<agent>/<session_id>.jsonl`（append-only，一行一条）
- 设备注册表 `l0_devices`：每台机器一条（设备码 / 可读名 / 设备信息 / agents / 首末次上报），
  是跨机归类的依据；`l0_batches` 记批次指纹与 `device_code`
- 路径片段白名单化，防目录穿越；读会话内容前先校验归属（防跨用户越权）
- 容量参考：单机 ZCode 实测 82 会话 ≈ 3.5 万条 ≈ 147MB，稳态增量很小

## 7. 查询接口

| 接口 | 用途 |
|---|---|
| `GET /api/l0/stats` | 总览 + 设备清单 + 会话清单（含每设备会话数/条数/体积） |
| `GET /api/l0/stats?device=<设备码>` | 只看某台机器的会话（跨机查看的核心） |
| `GET /api/l0/stats?device=<设备码>&agent=<agent>` | 再按 agent 收窄 |
| `GET /api/l0/session?agent=&device=&session_id=` | 读单个会话的逐条内容（Web 详情用） |

Web 端「会话归档」页按 **设备 → agent → 会话 → 详情** 四级下钻（逐级选择才展开下一级，
避免一次列出全部会话）：

1. **设备** — 每台装机器的可读名 / 设备码 / 系统 / agents / 会话数 / 体积 / 最近上报
2. **Agent** — 选中设备后，列出该设备下各 agent 的汇总（会话数 / 条数 / 体积 / 最近活跃，按最近倒序）
3. **会话** — 选中 agent 后才列出会话（会话 id / 条数 / 体积 / 首次与最近时间）
4. **详情** — 点会话看逐条内容（用户/助手/工具/推理分类 + 原文展开）

> agent 层级与之后的两级是**本地派生**的：选中设备时一次性取回该设备全部会话，
> 再切 agent 不再请求接口。切换设备会清空 agent 选择（agent 与设备强绑定）。

## 11. 数据敏感性与边界

**原始会话是整个链路里最敏感的数据**——含你与 agent 的全部对话，可能包含粘贴的源码、
口令、内部文档。本方案只保证"不被 AI 加工"，不等于不敏感：

- 归档默认**不加密**（与 L2 记忆一致）；如需加密应在磁盘/传输层做（HTTPS + 加密盘）。
- 服务端能读到原文的人即拥有等同密钥的权限，`data/l0/` 访问权限需按此控制。
- 采集范围、保留期限、谁可访问，属你自己的部署决策，不在技术实现内自动决定。
- 建议先在试点范围（单机/单组）验证体量与隐私边界，再决定铺开。

## 12. 后续（L1）

L0 只存不用就是纯囤积。下一步应做 L1：以 `rid` 为键消费归档文件（offset 游标），
对每个会话生成摘要（目标 / 关键决定 / 未决事项 / 产出物），再做 L2/L3 的凝练。
L1 消费时须按 `rid + version` 取最大版本收敛——这是 L0 允许重复观察、且 ZCode 会原地更新
所要求的。
