# 四层记忆架构与进展

> 本文是「四层记忆」重构的总览与进度台账：每层做什么、当前落到哪、下一步是什么。
> - 架构源起：[调研报告-2026-07-会话与记忆管理系统.md](调研报告-2026-07-会话与记忆管理系统.md)（L0-L3 分层模型出自该文第 3 节）
> - L0 实现细节：[L0-原始会话归档.md](L0-原始会话归档.md)

## 1. 为什么分层

原始需求是两件事：**多 agent 原始会话自动备份** + **自动凝练成多层记忆**。业界共识是把两者分开：

- **原始层只追加、不修改**（备份/审计/重放），是唯一事实源；
- **凝练层由后台流水线异步生成**，可从原始层重放重建；
- 这样凝练逻辑升级时不丢数据——想换算法，把 L0 重跑一遍即可。

一句话：**L0 是 source of truth，上层都是可再生的派生视图。**

## 3. L0 已确定的接口（上层据此消费）

L0 与上层之间只有一个契约：**归一化记录流**。字段与可靠性保证见 L0 文档；上层必须知道的三条：

1. **按 `rid + version` 取最大版本收敛**——同一记录可能被观察多次（ZCode 会原地更新内容，
   version 递增），L1 消费时取最大 version 才是最终内容。
2. **L0 允许重复行**——去重是 L1 的职责（服务端已按 `(设备,agent,会话,rid,version)` 拦掉精确重复，
   但不同 version 的多份观察会保留，供收敛）。
3. **设备维度不可忽略**——记录带 `_dev`/`_agent`，同一个人多台机器的会话是不同数据源。

## 4. 当前架构

```
各台设备                                    aimemory 服务端
┌──────────────────────────┐                ┌────────────────────────────┐
│ 采集器（pm2 常驻·死程序） │  POST          │ /api/l0/ingest（幂等+去重） │
│  adapter: codex/claude/  │ ────────────►  │   ↓ append                 │
│           zcode          │  /api/l0/     │ data/l0/<用户>/<设备>/<agent>/ │
│  游标+spool队列+设备指纹  │   ingest      │   ↓                        │
└──────────────────────────┘                │ /api/l0/stats·session 查询  │
                                            │ Web「会话归档」三级下钻      │
                                            └────────────────────────────┘
```

关键设计取舍（都是实测踩出来的，详见 L0 文档）：

- **上传层冻结**：只认归一化 schema，新增 agent 只加 adapter；adapter 必须**流式 emit**，不整轮攒内存。
- **设备用机器指纹统一**：`machine-id` 优先、物理 MAC 兜底，重装后仍认回原设备。
- **原始会话最敏感**：含全部对话原文，不加密，`data/l0/` 权限等同密钥权限（见 L0 文档第 11 节）。

## 5. L1 已实现（会话摘要）

后台把静默的归档会话摘成结构化情景记忆。实现要点：

- **输入收敛**：按 `rid + version` 取最大版本（L0 允许重复观察、ZCode 原地更新，
  不收敛会摘要到「写了一半」的内容）
- **预算化压缩**：单会话平均 299K 字符、最大 4.6M，远超 LLM 上下文。按
  「user 全文 > assistant 正文 > tool 仅名字 > reasoning 丢弃」装配，超预算保留头尾。
  两个实测关键点：
  1. **系统注入内容必须滤除**——归档里 56% 的 user 记录是 agent 塞进来的系统提醒
     （TodoWrite、system-reminder、task-notification 等），不过滤会把这些当成用户诉求
  2. **工具序列合并同名计数**——某会话 7106 条里 3788 条是 tool，合并后只剩几十行
- **输出**：每会话一条（概述 / 关键决定 / 未决事项 / 产出物），落 `l1_summaries` 表
- **触发**：会话静默 5 分钟后排队（正在变的不摘）；用 `l0_records` 的
  count/version 聚合指纹判断是否变化，未变则跳过、变了则重跑
- **出口**：MCP `list_session_summaries` / `get_session_summary`、REST `/api/l1/*`、
  Web 会话详情顶部
- **成本**：单会话约 90-110 秒（本地 LLM 思考模型；`max_tokens` 需 8000——
  实测设 1500 会因思考耗尽预算导致 content 为空）

### L1 的两个坑（已修，有回归测试）

| 现象 | 根因 | 处置 |
|---|---|---|
| 摘要只有一句、数组全空 | 思考模型把 token 预算烧在 reasoning 上，content 为空，而 reasoning 兜底把「盘算过程」当正文返回 | `max_tokens` 提到 8000；**非 JSON 输出判失败而非降级存下** |
| 摘要请求 30s 超时 | LLM 客户端默认超时适用于短任务，大输入摘要需 ~90s | `complete()` 支持 `timeoutMs` 覆盖，摘要用 240s |

## 6. L2 已完成（冲突消解 + 派生链）

L2 原先只有"抽取"这一半：素材经 LLM 提炼成事实后**纯追加**入库，不与已有记忆比对——
同一事实反复入库、新旧取值并存互相矛盾。2026-09-18 补齐了缺失的另一半：

- **四操作冲突消解**（mem0 式）：入库前与已有记忆比对，产出 `ADD` / `UPDATE` / `DELETE` / `NOOP`。
  判定与素材提炼合并为**同一次 LLM 调用**（省 token）；候选召回用 FTS5 trigram + 短词兜底，
  **不依赖 embedding**（embedding 在本项目是可选组件）。
- **安全阀**：`target` 必须落在候选集内且属于该用户（防幻觉 id 误删）；单批 DELETE 有上限；
  判定失败/输出不可解析 → 降级为纯追加（增强功能绝不能让事实丢失）。
- **`DELETE` = 删旧 + 存新**（取代语义）：真实模型实测发现——面对"端口从 A 改成 B"，
  模型倾向选 `DELETE` 而非 `UPDATE`；若 DELETE 只删不存，新取值会凭空消失。
- **审计**：`memory_ops` 记录每次判定（`before_text` 保留被删原文，误删可复原）。
- **派生链**：L2 可从 L1 摘要派生事实（`l1:<agent>/<会话>` 可溯源），后台静默触发 +
  内容指纹幂等，改 L1 算法后可整体重跑——这才真正兑现"上层可从 L0 重放"。
- **向量层可插拔**：`sqlite-vec` 索引替代"全表读出 + JS 逐条算余弦"；扩展缺失/维度不匹配
  时自动降级关键词，不影响功能。

细节见 [L2-事实记忆与冲突消解.md](L2-事实记忆与冲突消解.md)。

## 7. 下一步：L3 画像／知识

L1 落地后，「这个会话/这台机器做了什么」已经能查。L3 是更长周期的凝练：

- 输入：L1 摘要 + L2 事实记忆（两者都已有）
- 产出：用户画像 / 项目约束 / 经验教训——低频、高价值
- 关键设计：**双时间轴**（事实何时为真 + 何时入库），旧事实不删只标记 superseded，
  这样「我以前的偏好是什么、什么时候变的」可追溯
- 形态可先轻量：Markdown 文件（人工可审阅可编辑）起步，需要时再引入结构化存储
