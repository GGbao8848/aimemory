## 1. 需求拆解

需求其实是两件事，业界通常分开解决：

| 子需求 | 本质 | 对应业界概念 |
|---|---|---|
| 多 agent 原始会话自动备份 | 会话的**持久化/归档**（append-only，可回放、可审计） | Session persistence / Checkpointing / Conversation archive |
| 自动凝练成多层记忆 | 从原始会话中**抽取→更新→分层**出长期记忆 | Memory extraction & consolidation（mem0 的核心） |

关键设计原则（业界共识）：**原始层与凝练层分离**。原始会话只追加、不修改（备份/审计/重放）；凝练层由后台流水线异步生成，可重建（从原始层重新跑一遍即可恢复）。这样凝练逻辑升级时不用丢数据。

## 2. 主流方案调研

### 2.1 Mem0（最接近需求形态）

- **定位**：独立的"记忆层"服务，挂在任意 agent 框架外，API 形式接入。
- **核心流水线（两阶段）**：
  1. **Extraction（抽取）**：每轮 user/assistant 消息对 + 最近历史上下文，交给 LLM 抽取候选记忆（事实、偏好、决定）。
  2. **Update（更新）**：把候选记忆与向量库中相似已有记忆比对，通过 tool-call 机制决定 `ADD / UPDATE / DELETE / NOOP`——这是它"自动凝练"的关键：新事实会**改写**旧记忆而不是无限堆积。
- **2026 新增**：`auto-dream` 后台整合（gated consolidation）——合并重复、丢弃过期/敏感条目、重写模糊记忆；支持"技能"式记忆就地加载。
- **优点**：接入成本最低（一个 SDK 调用）；token 开销小（论文报告每会话约 1,764 tokens 记忆足迹）；开源 + 托管双模式。
- **缺点**：记忆是扁平的"事实条目"，**没有显式多层结构**；不管理会话本身（会话备份要自己做）；多 agent 共享/隔离靠 `user_id / agent_id / run_id` 三个 scope 参数，粒度够用但无层级。
- **对本需求的匹配度**：凝练流水线可直接借鉴；会话备份需自建。

### 2.2 Zep / Graphiti（时序知识图谱路线）

- **定位**：记忆层服务，核心是开源引擎 **Graphiti**（时序知识图谱）。
- **核心机制**：
  - **双时间轴（bi-temporal）**：每条事实边同时记录 `valid time`（事实何时为真）和 `ingestion time`（何时入库）。事实被推翻时**不删除**，标记 superseded，历史可查——天然适合"记忆演化"。
  - **多子图分层**：Episode 子图（原始事件/会话片段）→ Entity 子图（实体与关系）→ Community 子图（社区摘要）。这实际上就是**三层记忆**：原始层 / 实体层 / 摘要层。
  - 增量构建：新会话进来只更新受影响的子图，不用全量重建。
- **优点**：LoCoMo 基准 71.2%（对比 MemGPT 的 66.9%），延迟还低 18%+；"事实何时变过"可追溯，审计友好。
- **缺点**：架构重（需要图数据库 Neo4j/FalkorDB）；记忆足迹大（Mem0 论文指其每会话可超 60 万 tokens）；对简单场景是杀鸡用牛刀。
- **对本需求的匹配度**：Episode→Entity→Community 的分层模型最值得抄；图数据库可先降级为 JSON/SQLite 实现。

### 2.3 Letta / MemGPT（agent 运行时 + 自管理记忆）

- **定位**：不是记忆库，而是**有状态 agent 运行时**（OS 隐喻：上下文=内存，外部存储=磁盘）。
- **核心机制**：
  - **三层记忆**：Core memory（常驻上下文的自编辑块，如 persona/user 画像）→ Recall memory（会话历史，可检索）→ Archival memory（向量库长期存储）。
  - **agent 自己管理记忆**：模型在正常循环里调用 `core_memory_replace`、`archival_memory_insert` 等工具决定记什么——记忆管理是 agent 的"一等公民"行为。
  - **Sleep-time compute**：空闲时后台 agent 对记忆做整理、预计算、自我反思（"睡眠期"凝练），不占在线延迟。
- **2025-08 基准**：Letta 团队在 LoCoMo 上发现——**仅用文件系统存会话历史就能拿 74.0%**，超过 Mem0/LangMem/Zep 的多数配置。结论：检索基准上"存好原始会话 + 好的检索"比复杂凝练更重要；复杂记忆系统应作为工具插进 agent 框架。
- **优点**：分层最完整、最透明（记忆块可人工查看编辑）；sleep-time 思路与"自动凝练"高度一致。
- **缺点**：要换它的 agent 运行时（或至少用它的 memory 模块）；对"多 agent 会话备份"没有现成方案。
- **对本需求的匹配度**：Core/Recall/Archival 三层 + sleep-time 后台凝练，是"多层记忆"的最佳参考架构。

### 2.4 LangMem（LangChain 系）

- 定位：LangGraph 生态的记忆工具库，提供 memory manager（抽取/更新/反思三种策略）+ 语义/情景/程序性记忆分类。
- 优点：与 LangGraph 的 checkpointer（会话持久化）天然配套——**会话备份（checkpointer）+ 记忆凝练（LangMem）正好覆盖本需求两块**。
- 缺点：绑定 LangGraph 生态；记忆能力相对基础（社区评价"solid for basic lookups"）。

### 2.5 会话持久化/备份的通用做法（与记忆系统解耦）

- **LangGraph Checkpointer**：每个 super-step 存一次图状态快照，按 `thread_id` 组织；支持 SQLite/Postgres/Redis 后端。崩溃恢复、多轮续接、human-in-the-loop 都靠它。
- **通用模式**：
  - 会话 = 一个 append-only 的 JSONL/事件流文件（每行一条消息事件，含 agent_id、时间戳、token 数）；
  - 按 `agent_id / session_id` 分目录归档，定期压缩（gzip）+ 异地备份；
  - 凝练流水线消费这个事件流（offset 游标），产出写入记忆层。
- 这个模式**不依赖任何框架**，对"多 agent 原始会话自动备份"是最稳的底座。

### 2.6 评测基准（验收用）

| 基准 | 测什么 | 备注 |
|---|---|---|
| **LoCoMo** | 长对话多跳/时序/开放域问答 | 最常用；Zep 71.2%、MemGPT 66.9%、纯文件存储 74.0%（Letta 复测） |
| **LongMemEval**（ICLR 2025） | 500 题，6 类：信息抽取、多会话推理、时间推理、知识更新、弃答等 | 当前对话记忆"金标准"；2026 出 V2，强调 agent 记忆应支持写入+检索+更新全流程 |
| **DMR**（Deep Memory Retrieval） | 超长历史中的精确检索 | Zep 论文的主战场 |
| **Letta Memory Benchmark** | 固定框架/工具，只比模型的记忆管理能力 | 动态交互评测，比纯检索基准更贴近真实 |

## 3. 推荐架构（针对本需求）

```
┌─────────────────────────────────────────────────────────┐
│  L0 原始会话层（备份层）—— append-only，永不修改          │
│  sessions/<agent_id>/<session_id>.jsonl                 │
│  每条消息事件：{ts, agent, role, content, tokens, meta}  │
│  定期 gzip 归档 + 异地备份；可完整回放                    │
├─────────────────────────────────────────────────────────┤
│  L1 会话摘要层（情景记忆）—— 每会话结束/每 N 轮触发        │
│  由 LLM 生成：目标、关键决定、未决事项、产出物清单         │
│  存 sessions/<agent_id>/<session_id>.summary.md         │
├─────────────────────────────────────────────────────────┤
│  L2 事实记忆层（语义记忆）—— mem0 式抽取+更新             │
│  候选事实 → 与相似记忆比对 → ADD/UPDATE/DELETE/NOOP      │
│  向量库 + 元数据（scope: user/agent/project, 时间戳）     │
├─────────────────────────────────────────────────────────┤
│  L3 画像/知识层（长期凝练）—— 低频、高价值                │
│  用户画像、项目约束、经验教训；Zep 式双时间轴（事实何时变） │
│  人工可审阅、可编辑（Markdown 文件即可）                  │
└─────────────────────────────────────────────────────────┘
        ▲ 后台凝练流水线（sleep-time，空闲/定时触发）
        │  消费 L0 事件流（offset 游标）→ 产出 L1/L2/L3
        │  任何一层可丢弃，从 L0 重放重建
```

**要点**：

1. **L0 是唯一的 source of truth**。备份 = 把 L0 目录同步走（rsync/rclone 到 NAS 或对象存储），简单可靠。
2. **凝练是异步的**（Letta sleep-time 思路）：会话进行中不阻塞，空闲时批量处理；每层凝练都是幂等的，可重跑。
3. **L2 用 mem0 的 ADD/UPDATE/DELETE/NOOP 四操作**控制记忆膨胀——这是"自动凝练"不失控的核心机制。
4. **L3 用 Zep 的双时间轴**：记忆条目带 `valid_from / superseded_by`，旧事实不删只标记，画像演化可追溯。
5. **多 agent 隔离**：所有层按 `agent_id` 分目录/分 scope；跨 agent 共享的记忆（如用户画像）单独放 `shared/` scope，只读引用。
6. **检索**：L1/L2 向量检索 + L3 直接注入上下文（量小、高价值，常驻）。

**技术选型建议（轻量起步）**：

| 组件 | 起步方案 | 升级路径 |
|---|---|---|
| L0 存储 | JSONL 文件 + gzip | 不变（文件就是最稳的备份格式） |
| L1 摘要 | LLM 定时任务生成 Markdown | 不变 |
| L2 向量库 | SQLite + sqlite-vec / Chroma 本地 | Qdrant / pgvector |
| L3 画像 | Markdown 文件（人工可编辑） | 加双时间轴字段 |
| 凝练调度 | cron / 空闲钩子 | Letta sleep-time agent |
| 现成参考实现 | mem0（L2 流水线）+ LangGraph checkpointer（L0） | 整体换 Letta 运行时 |

**如果不想自建**：直接上 **mem0 托管/自部署**（L2 开箱即用）+ 自己写 L0 的 JSONL 归档脚本（半天工作量），L1/L3 用定时 LLM 任务补上。这是投入产出比最高的组合。

## 4. 落地路线（建议）

1. **第 1 周**：L0 会话备份跑起来（JSONL 归档 + 定时压缩 + 异地同步）。这一步独立可用，先解决"备份"刚需。
2. **第 2 周**：L1 会话摘要（会话结束钩子触发 LLM 摘要）。
3. **第 3-4 周**：L2 事实记忆（接 mem0 或自实现抽取+四操作更新）。
4. **之后**：L3 画像层 + 双时间轴；用 LongMemEval 子集做回归验收。
