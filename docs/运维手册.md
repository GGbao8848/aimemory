# 运维手册（随建设逐步补全）

## 首启自检与日常巡检

**首启自检**（部署后、启动前；依赖/目录/数据库完整性/LLM 配置/端口一次查清，缺什么给一行修复命令）：

```bash
npm run doctor                # 零网络调用；有 ❌ 退出码 1，可直接当部署卡点
npm run doctor -- --probe     # 追加探活 LLM/embedding 的 GET /models（≤4s，不耗 LLM token）
```

**健康检查**（监控探针友好；非 200 即异常）：

```bash
curl -fsS http://127.0.0.1:18543/healthz
# {"status":"ok","db":true,"embedding":"disabled","llm":true,"queue":{...},"time":"..."}
```

- `status: degraded` 的三种来源：db 打不开、已启用的模型服务探活失败、
  **提炼队列积压**（`queue.pending ≥ EVENTS_BACKLOG_WARN`，默认 50；`0` 关闭该判定）。
- `queue.pending` 持续增长 = 素材「收了但不处理」：先看 `pm2 logs` 里 LLM 调用报错，
  模型服务恢复后队列会自动消化；`failed` 事件不含素材原文，无需人工抢救。

## 备份与恢复

**备什么**：`data/aimemory.db`（全部结构化数据）+ `data/l0/`（原始会话，唯一事实源）+ `data/l3/`（画像条目，人工可编辑）。
三者缺一不可——L2/L1 都可从 L0 重放重建，但重放要烧 LLM 调用，直接备份是零成本方案。

**备份**（可加入 crontab，例如每天凌晨 3 点、保留 14 份）：

```bash
# crontab -e
0 3 * * * /path/to/aimemory/scripts/backup.sh /path/to/data /path/to/backups 14 >> /path/to/backups/backup.log 2>&1
```

脚本行为：
1. SQLite **在线备份**（better-sqlite3 `.backup()` API，一致性地包含 WAL 内容；绝不直接 cp .db 文件）；
2. `l0/`、`l3/` 目录 tar.gz 打包；
3. 生成 `manifest.sha256` 校验和清单；
4. 按保留份数清理旧备份。

服务运行中也可以备份（在线 API 读的是一致性快照）。

**恢复**（先停服务）：

```bash
pm2 stop aimemory-mcp            # 或 kill 掉 node src/index.js
scripts/restore.sh backups/20260919-030000 /path/to/data
pm2 start aimemory-mcp
```

脚本行为：sha256 校验 → 覆盖 db → 解包 l0/l3 → 打开库做 `integrity_check` 并打印表/记忆计数。
自检不过会非零退出，此时不要启动服务，换上一份备份重试。

**异地**：把 `backups/` 目录纳入你的同步体系（rclone/rsync 到 NAS 或对象存储）即可，备份目录自包含。
